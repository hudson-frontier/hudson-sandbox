# File transfer

## Implementation status

The Linux guest library implements bounded upload staging, atomic file publication, retained mutation receipts and captured downloads. Shared descriptors live in [`sandbox-protocol::files`](../crates/sandbox-protocol/src/files.rs); the engine is [`sandbox-guest::files::Transfers`](../crates/sandbox-guest/src/files/mod.rs).

The [authenticated guest protocol](guest-protocol.md#file-transfer-messages) and host `GuestClient` expose this engine. Guest boot creates `/workspace` and binds the file service to the same allocation/generation/boot as command execution. Controller-authenticated supervisor upload RPCs now retain dispatch intent and coordinate with allocation destruction. The optional supervisor download service uses separate reader credentials and expiring capture tickets. Authenticated [public downloads](api-contract.md#implemented-file-downloads) now resolve the current allocation and reauthorize before releasing responses. [Public uploads](api-contract.md#implemented-file-uploads) now persist bounded source reservations and run through controller claims. An opt-in source cleanup worker reclaims expired source bytes. Broader live/destroyed allocation history work remains tracked by [issue #79](https://github.com/hudson-frontier/hudsonbox/issues/79), and supported-host release acceptance by #28/#110; those gates are separate from the delivered file API.

## Workspace and path contract

`Transfers::open` accepts an existing absolute workspace directory selected by the caller and an allocation/generation/boot context. Guest boot selects `/workspace`; diagnostic service configuration selects an operator-provided directory, never a customer-supplied host path. The root's ancestors are trusted configuration; the final root component must be a directory and cannot be a symlink.

Transfer paths are canonical UTF-8 names relative to this root. Absolute paths, empty components, `.`/`..`, backslashes, control characters, components longer than 255 bytes and paths longer than 4096 bytes are rejected. Spaces and Unicode are allowed. There is no shell expansion, archive extraction or automatic parent-directory creation. The top-level `.hudson-transfers` name is reserved for internal state.

Subsequent lookup uses an open root descriptor and Linux `openat2` with `RESOLVE_BENEATH`, `RESOLVE_NO_SYMLINKS` and `RESOLVE_NO_XDEV`. Parent symlinks, magic links and mount crossings fail closed. There is no weaker fallback on kernels without these features. These are the kernel's [path-resolution restrictions](https://man7.org/linux/man-pages/man2/openat2.2.html).

Downloads and internal staged-file reads first pin an `O_PATH` descriptor, inspect its type and link count, then reopen the exact descriptor through an internally generated `/proc/self/fd` reference. This rejects FIFOs, sockets, devices, directories and multiply linked regular files before opening them for data I/O. Customer strings never become proc descriptor references.

Publication resolves the parent again, then uses that open directory descriptor. An existing final symlink or hardlink is replaced as a directory entry; its target is never opened or truncated. Existing directories cannot be replaced by uploaded files. This follows [rename semantics](https://man7.org/linux/man-pages/man2/rename.2.html). Renaming the already-open parent concurrently does not retarget its descriptor: publication applies to that pinned directory inode. This is not a promise that its pathname remains below the root after an adversary moves the directory.

## Upload and recovery contract

An upload descriptor binds an operation ID, relative path, declared size, SHA-256 and ordinary file mode (`0644` or `0755`). The versioned descriptor digest covers all fields. The retained receipt additionally binds allocation, generation and boot context. File bytes are absent from metadata and debug output.

1. `begin` checks the descriptor and current parent, reserves retained capacity, creates and syncs a staging file, then persists a staging receipt. An exact operation retry returns its existing receipt; a changed descriptor conflicts.
2. `write_chunk` accepts at most 32 KiB at a contiguous offset. Repeated bytes must match the existing prefix exactly. A partial write can resume by checking its written prefix and appending the rest. Gaps, mismatches, overflow and writes beyond the declared size fail. An acknowledgement follows the file sync.
3. `commit` verifies exact length and SHA-256, checks for detected changes during hashing, resolves the parent and applies the allowed file mode. It then persists and syncs `commit_intent` **before** renaming the staging file into place.
4. After rename, both affected directories are synced, then a `committed` receipt is persisted. Until publication, an existing destination remains unchanged. A completed operation never republishes on retry, even if a later workload changes or deletes the destination.
5. Any failure after commit intent leaves uncertainty. Reopening converts retained `commit_intent` to `unknown`; it never guesses whether the rename happened and never repeats it. `commit` on an unknown, committed or aborted receipt only returns that receipt.

A failed receipt persistence fences the current engine until it is reopened. Startup validates context, descriptor digests, retained counts and staging lengths. Missing staging for an admitted staging receipt or corrupt history fails closed. Validated orphan staging and temporary metadata can be removed; their names never authorize replay. A workspace lock prevents two engines from owning the same state concurrently.

`abort` applies only to staging: it retains an aborted receipt before removing bytes. It does not undo a committed or unknown mutation. Receipts and declared reservations remain in the public runtime. The internal [history retirement protocol](history-reclamation.md) coordinates database claims, acknowledged guest/host pruning and verified public reservation refunds through an opt-in controller worker. Deleting history without that durable admission fence remains unsupported.

## Downloads and bounds

`capture` pins a regular file, checks the size, reads a bounded byte sequence and rejects detected size/mtime/ctime changes during capture. Its digest covers exactly the captured bytes. Subsequent range reads use the captured buffer, so path replacement or later file writes cannot splice different versions into that handle. This is a captured byte sequence, **not an atomic filesystem snapshot**; metadata checks cannot prove consistency against malicious guest-root activity.

| Bound | Current behavior |
| --- | --- |
| File size | 8 MiB, including zero-length uploads |
| Chunk size | 32 KiB for uploads and captured download reads |
| Retained upload descriptors | 128 per workspace, including aborted, unknown and completed uploads |
| Retained upload reservations | 64 MiB of declared sizes per workspace; no automatic refund |
| Live captured downloads | Eight per workspace, each at most 8 MiB plus a one-byte growth check |
| Persisted metadata | At most 16 KiB per JSON file; bounded directory scanning |

A capture holds workspace ownership until dropped, including when the engine itself has been dropped. Reopening cannot bypass the live-capture bound. Returned chunks are borrowed slices; the transport must bound copies, connections, request lifetimes and total workspaces separately. The [file transport service](../crates/sandbox-guest/src/file_service.rs) uses one blocking worker and bounds its caller wait. Byte bounds and caller deadlines cannot interrupt stalled filesystem I/O.

Uploaded destination files consume the guest filesystem's ordinary capacity. The transfer reservation is not a substitute for disk quotas, and it cannot limit files that workload processes write themselves. A dedicated local writable filesystem with working `openat2`, directory fsync, file locks and same-filesystem rename is required; guest init creates the workspace, while release packaging and supported-host acceptance still need to verify this filesystem configuration.

## Trust and evidence

The guest runs customer commands as guest root. They can tamper with workspace data, agent state and reported receipts. The workspace path checks defend the file interface against unintended traversal; they do not turn the guest agent into an isolation boundary. Host allocation fencing, VM isolation, project authorization and host-side validation remain required. Guest metadata or `committed` is never proof of host cleanup, customer authorization or external-effect correctness.

[Protocol tests](../crates/sandbox-protocol/src/files.rs) cover canonical paths and descriptor identity. The [unprivileged Linux filesystem suite](../crates/sandbox-guest/tests/files.rs) covers bounded chunk retries, partial writes, restart, both durable commit crash windows, unknown rename failure, abort, history corruption, parent substitution, destination links, special-file rejection, retained limits, maximum-size round trip and stable bounded downloads. Run it on Linux with:

```sh
cargo test -p sandbox-guest --test files
```

The suite uses temporary directories and needs neither root nor KVM. [Authenticated transport evidence](evidence/2026-09-21-aarch64-file-transport.json) separately records guest TLS and a real Firecracker upload/execute/download round trip. These guest tests do not exercise the public route or prove supported-host isolation. Public authorization and transport are tested separately below; supported-host mount-policy and security acceptance remain release work.

## Transport handles and service lifecycle

The [file service](../crates/sandbox-guest/src/file_service.rs) dispatches typed requests into the engine after the listener has authenticated the peer and checked allocation/boot context. One semaphore permit bounds blocking file work. A busy worker rejects additional work without queuing it. A caller waits at most five seconds; a worker that outlives that wait or a disconnected caller retains the permit and workspace ownership until it actually finishes. These deadlines do not authorize replay of an uncertain mutation.

Each capture request is a **fresh read** and creates a fresh guest-generated capture ID. A capture response binds that ID to path, size and SHA-256. Range requests bind the handle and digest; the host validates the expected length, offset, next offset, total size and end marker. Callers assembling a whole file must also verify its full SHA-256. Echoing a digest in a range response is not whole-file verification.

Captures expire after 60 seconds of monotonic service time. The reported Unix deadline is a hint; it is not host-owned resource evidence. An idle reaper checks once per second without waiting behind file I/O, and requests prune expired entries before use. A stuck worker may delay physical buffer disposal while keeping all further file work blocked; the eight-handle bound still applies. Explicit release drops a matching capture, and repeated release is harmless. Missing, expired, released or pre-restart handles fail on read and never reopen their old path. A lost capture response can occupy one slot until expiry; making a new capture is a new read that may observe different bytes. Capture IDs and data are not persisted across agent restart.

Shutdown closes admission before draining the existing worker and clearing captures. If draining cannot be confirmed within five seconds, shutdown reports failure. Command shutdown is still attempted independently. The host guardian remains responsible for terminating a guest that cannot finish shutdown.

## Supervisor upload ownership and recovery

The controller-only `Supervisor` service exposes `BeginFile`, `WriteFile`, `InspectFile`, `CommitFile` and `AbortFile`. Each request carries the original upload descriptor and allocation ownership: host, project, sandbox, allocation, generation, supervisor epoch, operation ID, claim revision and deadline. The existing exact controller certificate pin protects every RPC; the output-reader certificate has no access, including to inspection, which can install a durable absence fence. File and command operation IDs cannot be reused across purposes.

[Host handlers](../crates/sandbox-supervisor/src/host/files.rs) serialize file operations with create, execution and stop through the allocation gate. New file admission checks capacity and durably installs its original descriptor digest, bound guest context, size and claim revision under one host journal lock. No guest request precedes that write. The retained host record contains neither the workspace path nor upload bytes. A host journal write failure closes further admission pending recovery.

A new `BeginFile` can forward once to the bound guest. A repeat inspects that operation. `CommitFile` and `AbortFile` persist their respective dispatch flags before forwarding once; subsequent calls inspect instead of repeating an uncertain mutation. A lost request or response can therefore remain unresolved when inspection finds no guest receipt. `WriteFile` may retry only while staging and before either terminal dispatch flag; the guest checks contiguous offsets and identical existing bytes. A `stored` cursor describes a confirmed acknowledgement from that call and is never persisted or inferred after a failed request.

Inspection or another file action before admission installs `not_started=true`; a later begin, even with a higher revision, cannot start it. An unfinished admitted operation with an unavailable or stopped guest returns state zero with `not_started=false`. This means **no current observation**, not successful publication or a safe fresh retry. Validated committed, aborted or unknown guest receipts remain retained; an unknown outcome never authorizes republishing. Even if an uncertain commit is later observed still staging, another commit is not dispatched. Abort can settle staging, but cannot undo committed or unknown publication.

The host retains at most 16 file operations per allocation and 1,024 across its journal, including absence fences and terminal records. Admitted uploads reserve at most 64 MiB of declared sizes per allocation, until acknowledged history retirement. New records must leave 256 KiB below the 16 MiB host journal limit for existing lifecycle work; compact file-state updates cannot grow their admitted metadata. This file-admission check does not redesign legacy command/allocation admission or establish universal journal reclamation. The fake host additionally bounds all simulated staged bytes to 64 MiB and drops its staging buffers on stop.

Stop and destroy use the same allocation gate. Unfinished file observations after stop cannot claim current staging or success. A new supervisor epoch rejects the old allocation owner and does not rebind its file operation to a new guest. Retained journals without a `files` field load as empty file history. Once file records exist, an older binary that rejects unknown fields cannot open that journal; rollback requires a compatible reader, not deleting operation history.

The shared [record tests](../crates/sandbox-protocol/src/supervisor_files.rs), [fake-host fault tests](../crates/sandbox-fake-host/tests/support/files.rs) and opt-in [real supervisor tests](../crates/sandbox-supervisor/tests/support/supervisor_files.rs) exercise these contracts. The fake tests inject reply loss; the real suite verifies authenticated publication, reconnect/retry behavior, retained metadata, full file capacity followed by destroy, and epoch fencing. [Recorded supervisor evidence](evidence/2026-09-21-aarch64-supervisor-files.json) includes matching source/artifact hashes and the validation history. Neither suite is a public file API or a general proof of isolation.

## Supervisor download service

An operator can enable `FileDownloads` on either supervisor with `--file-reader-cert-sha256`. Repeat the flag once for certificate rotation. This allowlist is independent of `--output-reader-cert-sha256`; neither controller nor output-reader credentials gain file access implicitly. File-reader pins must differ from controller pins. The service is absent when no file-reader pins are configured. Its `Capture`, `Read` and `Release` methods cannot upload files, execute commands or modify the durable lifecycle journal.

Each request carries a versioned read scope: host, host epoch, project, sandbox, allocation and generation, plus a deadline at most 30 seconds away. This is a descriptor supplied by an authorized API service, not a customer credential. The host checks that scope against the retained allocation and requires a live guardian/lease. The public API owns project authorization and revocation checks before and after every backend call.

Capture reserves an ephemeral host ticket before contacting the bound guest. The returned handle binds a fresh host ticket ID, allocation/generation/boot, the complete guest capture descriptor and a host expiry hint. Range and release requests must match the retained scope and every handle field. Changing the path, digest, size, guest capture ID, boot or expiry cannot retarget a handle. After guest I/O the host checks the current allocation and guest binding again, and rejects a stopped or changed allocation instead of returning its bytes.

The host retains at most eight tickets per allocation and 64 per host for 60 seconds of monotonic time from reservation. Pending, failed and released tickets continue to count until expiry; request processing prunes expired entries. Idle entries are already bounded and contain metadata only. Explicit release frees the guest buffer when acknowledged but keeps a host tombstone for retry safety. A release retry can acknowledge that same tombstone; an expired or missing ticket returns unavailable/not found and never recreates a capture. Host restart discards all tickets and rejects old ownership. A new capture is a fresh read with a new ID and may contain different bytes.

Four host download calls can be active at once, each with a four-second budget. Losing the caller does not abandon an admitted capture or release its worker slot before that task completes or times out. Uploads and downloads share one additional file slot per allocation: contention is rejected before upload dispatch intent is persisted. Stop does not wait for that file slot. These host deadlines cannot stop guest filesystem I/O; a guest worker may outlive the host request, retain its own permit and produce an unobserved capture that expires on the guest's schedule. The host ticket limit therefore bounds host metadata, not all guest capture memory across timeout/recovery windows. Guest captures remain bounded by the guest service and VM memory limits.

The fake host keeps bounded committed file bytes so upload-to-download behavior is testable. Staging plus published bytes share a 64 MiB global fake-memory limit; captured buffers have a separate 64 MiB global limit. A capture copies the current published bytes. Replacement cannot change an earlier capture; confirmed release or stop frees its buffer. Fake debug output excludes customer paths and file contents. These are simulation bounds, not measurements of real host memory.

The [shared descriptor validators](../crates/sandbox-protocol/src/file_downloads.rs) check scope, response provenance/time, capture identity and exact chunk cursors/length/end markers. Clients assembling a complete file must verify its full SHA-256. [Ticket and worker tests](../crates/sandbox-supervisor/tests/file_downloads.rs) cover forged handles/responses, monotonic expiry, both retained-ticket limits and caller detachment. [Fake round-trip tests](../crates/sandbox-fake-host/tests/support/file_downloads.rs) cover replacement, reply loss, expiry and captured-memory exhaustion. [Real reader tests](../crates/sandbox-supervisor/tests/support/file_downloads.rs) use dedicated file-reader credentials, supervisor uploads, verified binary downloads, reconnect, replacement, journal comparisons, destroy and epoch restart. [Recorded download evidence](evidence/2026-09-21-aarch64-file-downloads.json) includes matching source/binary hashes, all 13 host regressions and cleanup observations. Supported-host release acceptance remains unfinished.

## Private upload sources

The [source protocol](../crates/sandbox-protocol/src/file_sources.rs) and [source store](../crates/sandbox-artifacts/src/sources.rs) implement the durable object transport needed for public uploads. Public admission and controller dispatch now use this library through the `SourceBackend` interface. A successful object write does not publish a guest file, create a public operation, reserve database capacity or authorize customer access. The API and store perform those checks separately; the [source cleanup worker](#source-cleanup-worker) now schedules retirement. Remaining history reclamation is tracked by [issue #62](https://github.com/hudson-frontier/hudsonbox/issues/62).

Before invoking storage, the admitting service must persist one complete `SourcePlan` and reserve its byte budget. The plan binds the project, sandbox, operation, allocation, generation, host, host epoch, original upload descriptor, source attempt and all retention times. The upload descriptor includes the canonical workspace path, size, SHA-256 and ordinary file mode. The independently supplied `SourceOwner` includes the operation ID as well as allocation scope; the plan must agree with that operation, and another write in the same allocation is not an interchangeable owner. The source object key starts with `file-source/v1/` and contains only typed IDs and numeric ownership fields; the workspace path never becomes an object key. All metadata is bound by a domain-separated SHA-256 in the object's attributes. Credentials, paths and file bytes are excluded from library debug output.

`S3Config::build_sources` creates the typed source capability from private operator configuration. It uses the existing HTTPS, fixed-endpoint, no-redirect/no-proxy/no-ambient-credential client with automatic retries disabled. Explicit literal-loopback HTTP remains available for development. Operators must use a private source bucket or scoped source prefix and provision separate API write/read, controller read and cleanup credentials. The Rust capability shape does not replace storage IAM policy.

Writes are create-only. Exact concurrent/repeated writes verify the existing complete object; a changed descriptor or byte digest cannot replace it. `SourceRef` pins the ETag and optional version ID. Both reconciliation and controller reads verify all metadata, exact body length and full SHA-256 before returning any bytes. Truncated, extended, interrupted, mismatched or missing objects fail closed. A replacement worker can reconcile using only the persisted plan, without the original HTTP body or acknowledgement. It must retain that same attempt after uncertainty.

Plans distinguish the last time a new storage write may begin (`write_expires_unix_ms`), the end of source readability (`expires_unix_ms`) and earliest cleanup eligibility (`delete_after_unix_ms`). They must be ordered after a positive creation time. The library accepts authoritative time from its caller; it does not extend a database lease or validate project credentials. Reconciliation/read can continue after write admission expires, until read expiry. Checking an expiry at call entry cannot cancel a PUT already in flight, so the cleanup barrier below remains necessary. Admission must choose bounded service retention windows and recheck current authority before guest dispatch.

Each source is at most 8 MiB. Source and output operations share the existing four-slot process-wide storage limit and 30-second call timeout. The client connection/request budgets remain five/fifteen seconds. Source reads return a fully verified buffer, so callers must retain their own byte/concurrency reservations until they drop it. This library does not implement aggregate project/fleet storage quotas, HTTP body admission or database scheduling.

### Source retirement

`S3Config::build_source_retirer` creates a separate cleanup capability. Before calling it, the cleanup worker must freeze the exact persisted source attempt and selected reference, if any, in the database and confirm cleanup eligibility. Source retirement never grants an API write permission or a guest mutation.

Retirement conditionally replaces the original key with a compact marker, at most 16 KiB, binding the plan digest and any prior exact reference. A missing/unacknowledged source can be sealed without pretending that an empty file was uploaded. Competing cleanup calls and delayed create-only PUTs converge on that same key; future writes cannot recreate the payload over the marker. The marker must remain retained. Its metadata includes the original path within the private plan; it contains no file bytes. Finite marker/history reclamation needs a separate proven protocol.

For versioned buckets, cleanup verifies the complete previous version before deleting that exact version ID, then verifies its absence and the unchanged current marker. It never deletes an unqualified current key. An error, lost acknowledgement, false successful delete response or cancelled worker yields no completion receipt until recovery verifies those facts. In unversioned buckets, conditional marker replacement itself removes the old payload. Changes in bucket versioning that make the old and marker identities incompatible fail closed. Corrupt data or markers are retained for investigation rather than treated as absent.

[Source tests](../crates/sandbox-artifacts/src/sources/tests.rs) cover maximum and empty files, whole-object integrity, owner/descriptor changes, expiry, bounded work and debug redaction. [Retirement tests](../crates/sandbox-artifacts/src/sources/retirement/tests.rs) exercise races and failure recovery, including real MinIO version deletion and cancelled cleanup workers. The existing CI `output_minio` selection includes the new source cases. [Recorded storage evidence](evidence/2026-09-21-file-upload-sources.json) states the tested scope; this is object-storage evidence, not a public upload acceptance run or VM isolation claim.

## Public upload orchestration

[Admission](../crates/sandbox-store/src/uploads/admission.rs) authenticates the retained token hash, locks the project/sandbox and original allocation/host, and commits one normalized operation plus private `SourcePlan`. PostgreSQL serializes global source reservations; terminal or uncertain operations keep source bytes charged until verified storage retirement. Operation slots and declared guest byte reservations remain retained afterward. Source bytes never enter PostgreSQL. The HTTP handler verifies the whole body before admission, attempts the immutable PUT after committing, and revalidates credentials after I/O. Source errors preserve the admitted operation handle; retrying does not invent another source attempt.

[Dispatch](../crates/sandbox-store/src/uploads/dispatch.rs) validates the original project, sandbox, allocation, generation, host epoch, operation digest, plan and retained receipt on every claim. It checks the initiating token's original hash, project status, sandbox state/deadline and current host/allocation leases before new guest work. Token rotation under the same key ID cannot revive an old upload. Legacy unpinned `file_write` rows are retained but never claimed by this dispatcher.

The controller first reconciles the retained source, then commits begin intent before calling the supervisor. A lost begin selects inspection; a confirmed staging receipt permits bounded chunks. Only an acknowledgement for the exact dispatched chunk advances the database cursor. A lost chunk reply leaves the old cursor; after inspection, replay verifies the retained prefix. The controller caches at most one fully verified source (8 MiB) and sends at most 32 KiB per tick, rechecking authorization after source retrieval. Lifecycle maintenance runs before file work; a file step has a ten-second bound. This conservative loop makes no throughput or fleet-fairness promise.

Commit intent is durable before the RPC and is never dispatched again. Even if inspection subsequently reports staging, the controller continues inspecting until authority expires and a single abort is eligible. Abort cannot undo unknown or committed publication. Observation acceptance checks full claim ownership, descriptor digest, boot context, bounded acknowledgement, freshness, provenance and prior intent. Unavailable or destroyed guests do not turn uncertain writes into success or authorize replay.

Sources use a five-minute write window and one-hour read/delete-after times. These deadlines alone do not perform deletion. The independent source cleanup worker below freezes expired attempts and verifies storage retirement. The API and controller never call the retirement capability. Plans, receipts and markers remain retained. A separate opt-in [history worker](history-reclamation.md) reclaims operation slots and declared guest byte reservations only after source retirement and exact guest/host acknowledgement.

[Controller/API tests](../crates/sandbox-controller/tests/uploads.rs) exercise empty/binary/maximum bodies, real HTTPS above the JSON limit, malformed and foreign requests, concurrent retries, lost source/begin/chunk/commit replies, lost commit requests, source-read revocation, credential rotation, source/claim identity, unsolicited observations, fixed retained capacity and retry after destroy. [Migration tests](../crates/sandbox-store/tests/upgrade.rs) preserve legacy rows without inventing dispatch ownership. The MinIO-enabled [real host lifecycle](../crates/sandbox-supervisor/tests/host.rs) exercises public create → upload → execute → capture/download → destroy with a real Firecracker guest. Evidence records the tested environment; none of these tests proves that escape is impossible.

[Recorded public upload evidence](evidence/2026-09-21-aarch64-public-file-uploads.json) binds the final source/artifact hashes to 430 local tests, 14 real-host cases, the private MinIO fixture and verified VM cleanup. The guest was rebuilt for the final run; the temporary storage fixture was removed afterward.

## Source cleanup worker

`sandbox-cleanup --file-source-config /absolute/private/source-cleanup.json` enables expired upload source retirement. Configure the same bucket/endpoint used by upload admission, with separate cleanup credentials granting GET, conditional PUT and exact-version deletion. The file follows the existing owner-only [S3 configuration](output-storage.md#operator-configuration) rules. The worker accepts no guest/supervisor credentials and has no VM lifecycle authority. Revoked project credentials, destruction and later host epochs do not block cleanup of the original private source.

`--output-config` continues to enable output cleanup. Supply either configuration or both; neither domain is enabled implicitly by configuring the other. Both workers run concurrently when configured together. `--once` attempts one bounded tick per configured worker, reports each result and returns failure if either fails. Output response-retention/compaction flags require output configuration; they do not compact file metadata. Storage cleanup remains an operator opt-in, not an API-side action.

[Migration 0014](../migrations/0014_file_source_cleanup.sql) adds a frozen source manifest, independent cleanup revision/lease/retry state, and paired retirement receipt/timestamp to `file_uploads`. Existing rows gain empty cleanup state. [The store](../crates/sandbox-store/src/uploads/cleanup.rs) selects expired sources under operation/file row locks, waits for live operation leases to end, independently revalidates the original allocation and request digest, and freezes the exact plan plus any selected reference before storage I/O. Cleanup also waits until the operation deadline plus five minutes has passed: this covers the maximum issued operation claim, including a request whose lost reply cleared the database lease early. The default one-hour source retention is longer than that grace.

Frozen sources cannot gain a selected reference or authorize new begin/write/commit dispatch. Existing API retries keep their original operation handle and do not write source storage. The lifecycle controller can still inspect or abort the original guest operation. Freezing or retiring storage never invents a guest result, clears an uncertain operation or marks a sandbox released.

The [source worker](../crates/sandbox-cleanup/src/sources.rs) claims for 120 seconds, bounds database calls at five seconds (with two-second transactional statement bounds), and bounds processing at 60 seconds. It uses PostgreSQL time and the original frozen manifest for the existing 30-second storage retirement protocol. After verified deletion/sealing, completion rechecks ownership and the live cleanup claim after lock waits, validates the retirement receipt against the exact plan/reference, and commits once. An identical completion retry under the same retained revision acknowledges the existing result. Changed receipts or stale revisions cannot release capacity. Failed, cancelled or timed-out work retains its manifest and reservation; retry uses bounded exponential backoff, or claim expiry after worker loss.

Verified retirement releases only the global and project **source byte** charge. Admission computes these totals from unretired rows, so repeated completion cannot decrement a counter twice. Source cleanup alone leaves operation counts and the allocation's 64 MiB declared guest budget unchanged. The separate [history protocol](history-reclamation.md) can reclaim these after verified guest/host acknowledgement; original database identity/outcomes and storage markers remain retained. Destroyed/previous-epoch and marker reclamation remain unfinished. Expiry, destroy, a cleanup claim or an unverified delete response never refunds capacity. Corrupt or inconsistent source metadata fails closed for operator investigation.
